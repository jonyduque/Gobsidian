# CRÍTICO

## 1. Superfície de escrita não passa pelo confinamento de caminho

`internal/service/write.go:79` — `checkWriteAllowed` é uma checagem caseira que
**não chama `vault.Resolve`**:

```go
if strings.Contains(path, "../") || strings.HasPrefix(path, "/") || (len(path) > 1 && path[1] == ':')
```

Depois disso, `CreateNote:92` e `MoveNote:420` fazem
`vault.CanonicalPath(cleanPath)` — construção direta do tipo, forjando a prova
que o comentário de `CanonicalPath` promete ("o tipo e a prova de que o
confinamento ja rodou").

Traçando `note_create` com `path = "..\..\x.md"` no Windows:

| passo | valor |
|---|---|
| `checkWriteAllowed` | `Contains("..\\..\\x.md","../")` → **false**, passa |
| `filepath.Clean` | `..\..\x.md` |
| `vault.Abs` → `filepath.Join(root, ...)` | **dois níveis acima da raiz** |

`WriteAtomic` cria o temporário em `filepath.Dir(target)` e renomeia — os dois
fora do cofre. Vale para `note_create` e para o destino de `note_move`. Escrita
arbitrária no sistema de arquivos, pela tool que um modelo controla.

Em Linux a barra invertida não é separador, então `Contains("../")` pega o caso
equivalente — é bug específico de Windows, que é a plataforma primária do
projeto.

Junto vem a lacuna menor: `validateLocal` recusa nome de dispositivo via
`filepath.IsLocal` (a correção do `COM1`), e o caminho de escrita não a executa.
O efeito é atenuado porque `WriteAtomic` termina em rename, que falha sobre
dispositivo — mas a checagem não está lá.

**Correção:** `Resolve(root, input)` como único portão de todas as tools de
escrita, e `CanonicalPath` nunca construída por conversão fora de `vault`. Um
teste de mutação vale aqui: apague `checkWriteAllowed` inteira e veja quantos
testes falham — a suspeita é que nenhum cobre `..\`.

## 2. Construção do índice de busca baixa todo placeholder de nuvem

`cmd/gobsidian/serve.go:323`:

```go
data, err := v.ReadAll(ctx, p)          // não consulta IsCloudOnly
inv.Add(string(p), search.Analyze(string(body)))
```

O comentário de `Inverted.Update` (`internal/search/inverted.go:467`) afirma:
*"Sao tres pontos de chamada hoje — o laco de boot em buildInvertedIndex, o
watcher em Apply e a reconciliacao por overflow"*. Verificado por grep:
`inv.Update` é chamado por `watcher/apply.go:58,98`, `watcher/overflow.go:69` e
`cmd/gobsidian/search.go:46`. **`buildInvertedIndex` não está na lista.** A
guarda mora em `Update`; o laço de boot não passa por `Update`.

Pior: o teste que prova a regra tem o helper `construirComoOBoot`
(`cloudonly_update_windows_test.go:132`) documentado como *"tokeniza o cofre
exatamente como buildInvertedIndex faz: um Update por caminho"* — e ele chama
`inv.Update`, que a produção não chama. É um teste que não pode falhar pelo
caminho que ele nomeia, com a asserção certa apontada para o código errado.

Consequência exata: a armadilha que o `CLAUDE.md` registra ("trocar um crash por
download síncrono em massa... trava a máquina do usuário sem dizer por quê") está
**aberta em produção** na primeira `vault_search` de um cofre OneDrive.

## 3. `expected_hash` não protege contra o que existe para proteger

`write.go:172` e `write.go:278`:

```go
raw, err := os.ReadFile(absPath)                 // bytes do disco AGORA
currentHash := fmt.Sprintf("%016x", note.Hash)   // hash do ÍNDICE
if req.ExpectedHash != "" && currentHash != req.ExpectedHash { ... }
```

O hash comparado vem do índice de metadados, não de `raw`. Na janela do debounce
(padrão 250 ms) mais o tempo de `Replace`, uma edição externa já está no disco e
ainda não no índice: a checagem passa, e `note_append`/`note_patch` sobrescrevem
a edição do usuário. O controle otimista de concorrência falha exatamente no
cenário para o qual foi escrito. `xxhash.Sum64(raw)` está a uma linha.

## 4. Symlink dentro do cofre lê e escreve fora dele

`vault.Resolve` documenta o limite. Mas `Walk` usa `filepath.WalkDir` (Lstat):
um symlink chamado `nota.md` apontando para fora entra no índice como nota, e
`ReadAll`/`WriteAtomic` o seguem. `note_read` devolve conteúdo arbitrário;
`note_patch` escreve nele.

**Alternativa que não existia quando a decisão foi tomada:** `os.Root` /
`os.OpenRoot` (Go 1.24; o piso do projeto é 1.25.0). Confinamento imposto pelo
SO, resistente a symlink e a TOCTOU, com `Root.Open`, `Root.Create`,
`Root.Stat`, `Root.Remove`. Substituiria as duas camadas léxicas por uma
garantia real e tornaria o item 1 estruturalmente impossível. É a mudança de
arquitetura de maior retorno vista no projeto.

# IMPORTANTE

## 5. `ResolvePath` — varredura O(N) que só pode achar um, e `ErrAmbiguousPath` inalcançável

`index/resolve.go:273`:

```go
for lowerPath, realPath := range ix.lowerPath {
    if lowerPath == lower { matches = append(matches, realPath) }
}
if len(matches) > 1 { return "", ErrAmbiguousPath }
```

`lowerPath` é um mapa chaveado pela forma minúscula. Igualdade de chave casa **no
máximo uma** entrada. Então:

1. o laço é uma varredura de N entradas onde um `ix.lowerPath[lower]` responde em
   O(1) — e `ResolvePath` roda em toda tool de leitura e escrita;
2. `len(matches) > 1` nunca é verdade, e `ErrAmbiguousPath` por esse ramo é
   código morto — quatro tools tratam um erro que não chega;
3. a ambiguidade real de caixa é perdida **na escrita**, em
   `publishNameLocked:164` (`ix.lowerPath[lower] = path` sobrescreve). Num cofre
   Linux/macOS com `Nota.md` e `nota.md`, uma das duas fica inalcançável por
   nome, em silêncio.

## 9. `note_move` não é atômico e não tem recuo

`write.go:596-618`: lê o arquivo inteiro, `WriteAtomic` no destino,
`_ = os.Remove(absFrom)` — **erro descartado**. Se o remove falha (arquivo
travado pelo Obsidian no Windows, cenário comum), a tool devolve sucesso com a
nota duplicada nos dois caminhos, e o watcher indexa as duas.

Pior: as notas citantes já foram reescritas antes (linha 535). Se a leitura da
origem falhar depois, o retorno é erro **com os links já apontando para um
destino que não existe**. Não há rollback nem sequer registro do que ficou pela
metade. `os.Rename` resolveria o corpo; o lote de reescritas precisa de um plano
de compensação ou de uma ordem que falhe cedo.

## 10. `acceptLoop` do daemon morre em erro transitório

`daemon/daemon.go:152`:

```go
d.log.Warn("aceitar conexao no socket do daemon falhou", "err", err)
return
```

Qualquer `Accept` que falhe sem `ctx` cancelado encerra o laço **para sempre**.
`EMFILE`/`ENFILE` (limite de descritores) é transitório e clássico aqui. O daemon
segue vivo — `Run` continua no ticker — mas nunca mais aceita ninguém; e se ainda
houver uma conexão ativa, a ociosidade nem o encerra. Fica um processo zumbi que
toda ponte tenta usar e nenhuma consegue. Distinguir temporário de terminal, com
backoff.

## 11. `ipc.Listen` desvincula um socket vivo — é a causa dos dois daemons

`ipc/ipc.go:104` chama `cleanupSocketFile(path)` **incondicionalmente** antes do
`net.Listen`. Um daemon vivo tem seu arquivo removido; ele continua com o
descritor ligado a um inode sem nome, invisível para toda ponte futura, e sem
ociosidade se tiver cliente.

O `docs/OPERACAO.md` registra a corrida residual como propriedade do lock. O lock
não é a causa: o `Listen` é. O padrão consagrado é discar antes de desvincular —
`ECONNREFUSED` significa órfão e libera o unlink; sucesso significa abortar. Isso
transforma a mitigação probabilística em exclusão por construção, que é o que o
comentário de `lock.go:167` diz não ter.

## 12. `CloseWrite` é contrato declarado, verificado e nunca usado

`ipc.Conn` declara `CloseWrite()`, o doc comment explica o meio-fechamento, e
`DialAndHandshake:179` **recusa a conexão** se o tipo não o implementar. Grep: só
o dublê de teste chama. Em `servePonteRemota`, o EOF do stdin do host faz
`io.Copy(conn, teed)` retornar e o shutdown executa `conn.Close()` — matando a
resposta do daemon que estava em voo, que é precisamente o que `CloseWrite`
existiria para não fazer.

## 13. Flags da segunda ponte viram no-op silencioso

O handshake confere `ReadOnly` e `VaultKey`. `DebounceMS`, `CacheDir`,
`EagerSearch` (e `MaxResults`, se um dia funcionar) são os da **primeira** ponte
que subiu o daemon. Uma segunda ponte com `--debounce-ms=1000` conecta com
sucesso e é servida com 250. É o mesmo modo de falha que `ReadOnlySet` e
`DebounceMSSet` existem para impedir, um nível acima: ou os campos que mudam
comportamento entram no `HandshakeConfig`, ou a ponte avisa que a configuração
dela foi ignorada.

## 15. `garanteIndiceDeBusca` bloqueia sem respeitar o `ctx` de quem espera

`search_lazy.go:33` — `c.mu.Lock()` não é cancelável. A primeira busca dispara a
carga com **o ctx dela**; as concorrentes ficam presas no mutex ignorando os
próprios prazos. Numa construção do zero (minutos, no cofre de 109 MB), toda

## 16. `Replace` contorna `publishNoteLocked`

`publishNoteLocked` se declara "o ÚNICO lugar" que povoa os índices derivados, e
`Replace:113-127` reimplementa o corpo dele **mais** o registro de `byAlias` —
que `publishNoteLocked` não faz. Duas consequências: um campo derivado novo em
`publishNoteLocked` não chega a `Replace`; e `byAlias` depende de `buildAliasMap`
rodar depois nos caminhos de boot e de cache. A chave (`aliasKey`) foi
unificada; o **ponto de publicação** não. É a mesma lição, um nível acima da que
foi aprendida.

## 17. `WriteAtomic` — durabilidade afirmada e modo de arquivo perdido

`writer/atomic.go:85` promete "garantir a gravacao fisica no disco contra quedas
de energia". Faz `f.Sync()` no temporário, mas **não faz fsync no diretório**
depois do rename. Em ext4/xfs o rename pode não ser durável sem isso; a garantia
declarada é maior que a entregue.

Segundo: `os.CreateTemp` cria com 0600. Depois do rename, toda nota que passa por
`note_patch` fica 0600, mesmo que estivesse 0644. Num cofre em share de rede ou
sincronizado, isso muda a visibilidade dos arquivos em silêncio. `os.Chmod` para
o modo do original antes do rename.

## 18. `index.Build` descarta arquivo ilegível sem log nem contador

`build.go:73` e `:79` — `continue` seco em erro de leitura e de parse. A nota some
do índice, de todas as tools, e nada registra. Contraste com `vault.recordSkip`,
que existe justamente para isso e não é usado aqui. (O ramo de parse é
inalcançável hoje, por causa do item 14.)

## 19. `netcheck` não cobre as formas com receptor

`tools/netcheck/netcheck.go:74` exige `sel.X` ser um `*ast.Ident` que resolve
para o pacote `net`. Escapam:

- `d := net.Dialer{}; d.DialContext(ctx, "tcp", addr)` — receptor é variável
- `(&net.Dialer{}).Dial("tcp", addr)` — `sel.X` não é `Ident`, o `Inspect`
  retorna cedo
- `net.ListenConfig{}.Listen(...)`
- `syscall.Socket` / `golang.org/x/sys/unix` — e `x/sys` já está no módulo

A regra RNF-30 é declarada como garantia verificável. Ela é verificável para a
forma que o código usa hoje, não para a categoria. Vale banir os **tipos**
`net.Dialer`/`net.ListenConfig`/`net.Resolver` e as chamadas de socket via
`syscall`.

**Correção estrutural disponível: ver item 42.** `Dialer.DialUnix`/`ListenUnix`
(Go 1.26) põem a rede no *nome do método*, o que troca "provar que o argumento é
a constante `"unix"`" por "só estes dois métodos são permitidos" — regra mais
simples e impossível de furar por variável. Corrigir o analisador **antes** de
adotar, senão a chamada nova passa pelo buraco descrito acima.

## 20. CI não roda o quarto cenário de órfãos

`.github/workflows/ci.yml` chama `stdin-eof`, `parent-death` e `signal`.
**`daemon-idle` não está lá.** É o único mecanismo do daemon — que não tem pai
vigiável nem stdin de host — e é o único processo do produto que sobrevive à
saída do host. O `CLAUDE.md` conta a história de quando o padrão do script
cobria um de três; a mesma forma se repetiu com o quarto.

## 21. `link_graph` devolve ordem não determinística

Nenhum número abaixo é medido. Ordenado por impacto esperado. Cada item precisa

**Aviso que vale para a seção inteira, já corrigido por medição.** Os números que

## 22. `avgdl` do BM25 é O(N do cofre) por consulta

`search/bm25.go:91`:

```go
for _, p := range idx.Paths() {                 // aloca a lista inteira, notas + anexos
    if dl := ix.DocLength(string(p)); dl > 0 { sumDocLen += float64(dl) }
}
```

`idx.Paths()` aloca e ordena um slice de todos os caminhos, e `DocLength` pega
`RLock` a cada um. Num cofre de 4.513 notas: uma alocação de N strings mais N
aquisições de lock **por consulta**, para calcular um número que só muda quando o
índice muda. É o custo dominante que sobrou depois das Tasks 78-87.

`Inverted` já mantém `docLengths` e `sombraNoBase`; somar incrementalmente em
`Add`/`Remove`/`sombrearLocked` e guardar `somaDocLen int64` torna `avgdl` O(1).
Benchmark: `BenchmarkSearchLimit200Cache` deve mostrar o efeito escalando com o
tamanho do cofre, não com o número de resultados.

**Este item é subsumido pelo 36.** Pontuar em espaço de IDs densos resolve
`avgdl` como efeito colateral — `docLen` vira índice de array — e ataca junto o
custo maior, que são os milhares de mapas por consulta. Se os dois forem feitos,
fazer o 36; se só um couber, ainda assim o 36.

## 23. `getFieldWeight` roda por POSIÇÃO, não por posting

`bm25.go:80`:

```go
for _, pos := range p.Positions {
    fw := getFieldWeight(p.Path, pos, m.term, idx)   // idx.Get + RLock a cada posição
```

`idx.Get` (mapa + `RLock`) e `strings.Contains(n.TitleNorm, term)` são
invariantes na posição. Para um termo comum com milhares de ocorrências numa
nota, isso multiplica. Içar o `idx.Get` e a decisão de título para fora do laço;
só a checagem de heading depende de `pos` — e essa é O(#headings) linear, quando
`Headings` está ordenado por `Start` e admite busca binária.

Junto, uma **imprecisão de relevância**: `strings.Contains(n.TitleNorm, term)` é
substring, não termo. Buscar `ar` dá peso de título (3.0) a uma nota chamada
"Barra". Deveria casar limite de token.

## 24. `Heading.Slug` é pré-computado, persistido em disco e nunca lido

Este é o achado mais barato de corrigir do relatório inteiro.

`ExtractHeadings` (`parser/headings.go:64`) preenche `Slug: Slug(title)` em todo
heading. `persist_codec.go:186` **grava esse slug no cache de metadados**. E
nenhum leitor o usa — todos recomputam:

| ponto | o que faz | contexto |
|---|---|---|
| `index/anchors.go:31` | `parser.Slug(h.Text)` **dentro do laço** sobre headings do alvo | por link com âncora, em `resolveAllLinks` no boot |
| `service/read.go:173` | `parser.Slug(h.Text)` dentro do laço | por `note_read` com `heading` |
| `writer/section.go:59` | `parser.Slug(h.Text)` dentro do laço | por `note_append`/`note_patch` com `heading` |

`Slug` constrói `transform.Chain(norm.NFD, runes.Remove(...), norm.NFC)` a cada
chamada, sem pool. `resolveAllLinks` no boot é, portanto, O(links × headings)
construções de chain — num cofre jurídico cheio de `[[nota#Art. 5]]`, é caro. E o
valor correto já está no campo ao lado, pago no parse e persistido.

Trocar `parser.Slug(h.Text)` por `h.Slug` nos três pontos é uma linha cada.
Cuidado: `Slug` mudar de comportamento passa a exigir bump de
`IndexCacheParserVersion`, porque o valor está no cache — o que já é a regra
documentada em `persist.go:24`.

Sobra, ainda assim, o problema de fundo: **três implementações independentes da
mesma normalização** convivem.

| função | pool | onde |
|---|---|---|
| `text.Normalize` | **sim** (Task 78) | `internal/text/normalize.go` |
| `index.normalizeString` | não | `index/query.go:41`, filtro de frontmatter |
| `parser.Slug` | não | `parser/slug.go:19` |

É a mesma disciplina que o projeto já aplica a `aliasKey` e `nomeChave`, não
aplicada aqui.

## 25. `IsCloudOnly` é um syscall por arquivo, evitável

`vault/walk.go:185` chama `IsCloudOnly(abs)` para **toda** entrada; no Windows é
um `GetFileAttributes` por arquivo, no boot e em cada `VerifyFreshness`. Mas
`d.Info()` na linha 174 já foi obtido, e no Windows ele vem preenchido do
`FindFirstFile` da varredura — sem syscall.
`info.Sys().(*syscall.Win32FileAttributeData).FileAttributes` traz os mesmos bits
de graça. Elimina N syscalls por varredura.

(`Inverted.Update` também paga um por nota — lá o syscall é necessário, porque
não há `FileInfo` em mãos.)

## 26. `index.List` recomputa `ToLower` por comparação

`query.go:372`: `switch strings.ToLower(q.Sort)` está **dentro** do comparador
passado a `SortStableFunc` — O(n log n) alocações de string para um valor
constante. Idem `strings.ToLower(q.Order)` fora (esse está certo). Içar para fora
e escolher a função de comparação uma vez.

Menor, na mesma função: `cmp = int(a.Size - b.Size)` trunca `int64` para `int`
(inofensivo em 64 bits, quebra em 32). `cmp.Compare(a.Size, b.Size)` é o idioma
de Go 1.21+.

## 27. `Analyze` sem pré-alocação nem caminho rápido ASCII

`search/analyzer.go:78` — `var tokens []Token` cresce por append em documento
inteiro; um `.md` de 100 KB gera dezenas de milhares de tokens e ~20
realocações com cópia. `make([]Token, 0, len(text)/8)` mata isso. E o laço
decodifica runa a runa com `utf8.DecodeRuneInString` + `unicode.IsLetter`; para
`r < utf8.RuneSelf` (a maioria esmagadora dos bytes) uma tabela de 128 posições
é muito mais barata. Isto é o custo dominante da construção do índice de busca —
o número de 219 s no cofre de 109 MB sai daqui.

Nota de estilo: o parâmetro se chama `text` e sombreia o pacote `text`
importado. Funciona só porque a chamada passa pelo wrapper local `Normalize`.
Frágil.

## 28. `GenerateSnippet` re-tokeniza termos já tokenizados

`snippet.go:78`: `toks := Analyze(termStr)` — mas `rawTerms` que chega já é
`tok.Raw` de tokens analisados em `service.Search`. Com `limit: 200`, são
200 × (#termos) análises redundantes de strings de uma palavra. Passar os
`search.Token` em vez de `[]string`.

## 29. `matchPhraseInNote` — busca linear e regra de adjacência quebrada

`service/search.go:432`:

```go
if posN.Start >= currEnd && posN.Start <= currEnd+1 {
```

Exige que o token seguinte comece no máximo **1 byte** depois do fim do anterior.
`"foo bar"` casa; `"foo  bar"` (dois espaços), `"foo, bar"`, `"foo — bar"`
(travessão, 3 bytes) e quebra de linha CRLF **não casam**. A busca por frase
exata falha em silêncio na maioria da pontuação real. É correção, não
desempenho: a regra deveria ser ordinal (posição de token), não distância em
bytes — o que exige guardar o índice ordinal do token, hoje ausente do
`TokenPosition`.

O laço interno também é linear sobre listas que estão ordenadas; busca binária
resolve para termos comuns.

## 30. `note_read` não tem `offset` — a lacuna que causou o incidente

`noteReadInput` (`mcpsrv/tools_read.go:274`) aceita `path`, `paths`, `heading`,
`heading_level`, `block_id`, `include_frontmatter`, `max_bytes`. **Não há
`offset`.** As únicas formas de recortar são heading e bloco; falhando as duas,
resta ler tudo — e "tudo" são 255 KB que o host recusa.

`vault.ReadRange(ctx, path, start, end)` **já existe**, já é usada pelo recorte de
trecho, já tem teto de alocação e já valida a faixa. `service.ReadNote` já calcula
`start`/`end` e chama `ReadRange`. Falta um campo no schema e três linhas no
handler.

Isso, sozinho, teria resolvido o incidente: o modelo pagou 255 KB uma vez em outro
servidor justamente para fatiar por posição — a operação que ele queria era
`note_read(path, offset=N, max_bytes=8000)`.

## 31. A âncora do trecho é a primeira ocorrência do PRIMEIRO termo da consulta

É a causa exata do trecho vir do topo do arquivo. `search/snippet.go:77`:

```go
for _, termStr := range queryTerms {      // ordem da CONSULTA
    for _, tok := range Analyze(termStr) {
        for _, t := range termsToSearch {
            posicoes := ix.Positions(t, string(cPath))
            if len(posicoes) > 0 {
                bestMatch = &matchPos{ start: posicoes[0].Start, ... }  // PRIMEIRA do documento
```

A consulta `"13.1.10 Substituição de candidatos"` tokeniza como
`13, 1, 10, substituicao, de, candidatos`. O primeiro termo é `13`; a primeira
ocorrência de `13` no documento é o título `**13**`, no offset ~0. O trecho ancora
ali e nunca chega perto da seção 13.1.10, que fica muito adiante.

A variável se chama `bestMatch` e não há escolha nenhuma: é a primeira que
aparece. Três defeitos empilhados:

1. **Ordem da consulta em vez de seletividade.** Deveria ancorar no termo de maior
   IDF — `substituicao` acharia a seção; `13` nunca acha. O IDF já é calculado em
   `CalculateBM25` e descartado antes de chegar aqui.
2. **Primeira ocorrência em vez da melhor.** Uma janela deslizante que maximize a
   densidade de termos distintos da consulta é o algoritmo padrão, e as posições
   de todos os termos já estão em mãos.
3. **Consulta por frase ignora o casamento da frase.** `matchPhraseInNote`
   (`service/search.go:411`) **calcula a posição exata do casamento** para decidir
   se o hit entra no resultado, e joga o valor fora. Quando a consulta vem entre
   aspas, essa posição é a âncora óbvia e correta, e ela já foi computada.

O sintoma que o usuário vê: a busca por frase exata encontra a nota certa e
devolve um trecho que não contém a frase. Que foi exatamente o que aconteceu.

**Suspeita não verificada, a testar:** o segundo resultado da sessão
(`Resumo - Claude - Direito Eleitoral.md`) muito provavelmente não contém a frase
`13.1.10 Substituição de candidatos`, e ainda assim passou pelo filtro de frase. Se
confirmado, é o falso positivo previsto no item 29 — a regra de adjacência por
byte (`posN.Start <= currEnd+1`) casando tokens que só estão perto, não em
sequência. Teste que responde: `matchPhraseInNote` contra um corpo que tenha
`13`, `1`, `10` e `candidatos` espalhados mas nunca contíguos.

## 32. `HEADING_NOT_FOUND` com lista vazia não diz o que houve

`service/read.go:187`:

## 33. Estrutura em negrito não é reconhecida como seção

`parseATXHeading` (`parser/headings.go:93`) só aceita ATX (`#`). Não aceita:

- **negrito como título** — `**13.1.10 Substituição de candidatos**`, que é o
  formato da nota do incidente e o que qualquer conversão de PDF/DOCX/EPUB produz;
- **setext** — `Título` seguido de `====` ou `----`, que é CommonMark válido e o
  que vários conversores de Markdown emitem.

Consequência: `note_read` por heading, `note_patch` por seção, âncoras de wikilink
(`[[nota#Seção]]`) e o peso de heading do BM25 **não funcionam em nenhuma nota
convertida de livro**. Num cofre de estudo, isso é a maioria do material.

## 34. `snippet_chars` é clampado em silêncio

`service/search.go:138` corta em `search.MaxSnippetChars` (1000). O modelo pediu
4000 e recebeu 1000, sem aviso e sem o máximo declarado no schema
(`tools_read.go:269` é um `*int` sem descrição). Mesma família dos itens 7 e 8:
quem lê o schema para decidir não tem como saber que o pedido foi reduzido. Ou
declarar o teto no `jsonschema`, ou devolver o valor efetivo na resposta.

## 35. `vault_search` não devolve o offset do casamento

relatório com o maior efeito sobre este caso.

## 45. Lote sem parâmetro por item — `heading` vale para todos ou nenhum

Relato: *"heading só funciona por path único — pra 6 capítulos preciso de 6
chamadas paralelas, não uma só com lista."*

Preciso sobre o mecanismo: `paths` **e** `heading` funcionam juntos —
`tools_read.go:96` repassa `Heading` a `ReadNotes`, que o aplica a cada caminho.
O que não existe é `heading` **diferente por item**. Seis capítulos com seis
seções diferentes exigem seis chamadas.

`ReadBatchRequest` documenta a escolha: *"não há campo por-item porque o schema
de entrada é plano"*. A decisão é coerente, mas o custo caiu inteiro sobre o
caso de uso mais comum — percorrer capítulos distintos de uma obra.

Duas saídas, e a segunda é melhor:

- `items: [{path, heading}, ...]` como forma alternativa a `paths`. Resolve, mas
  cria uma terceira forma de entrada ao lado de `path` e `paths`, e a regra de
  exclusão mútua vira ternária.
- **`paths` aceitando objeto ou string**: `["a.md", {"path":"b.md","heading":"X"}]`.
  Os campos de topo continuam sendo o padrão, e o objeto sobrepõe por item. Uma
  forma de entrada, não duas.

Vale para `max_bytes` e `block_id` pela mesma razão.

## 46. Truncamento sem continuação — segunda observação do mesmo defeito

Relato: *"Truncamento em capítulo grande (XI, ~56KB): sem max_bytes ajustável
nem paginação — precisa reler do arquivo persistido à parte, um passo extra."*

primeiro pedaço, não há como pedir o resto. Sem `offset`, `max_bytes` só escolhe
o tamanho do que se perde.

Que a percepção tenha sido "sem max_bytes ajustável" é informação sobre o
schema, não erro de quem relatou: um teto sem par de continuação não se parece
com um controle, se parece com um limite. E `Truncated: true` — que ainda por

## 47. Caminho com caractere especial na escrita — o risco real não é o travessão

Relato: *"não sei ainda se aguenta path com caracteres especiais tipo '—' nos
nomes."*

Verificado por leitura, não por teste:

**O travessão em si é seguro.** `—` (U+2014) é só bytes UTF-8, sem significado
para `filepath.Clean`, para `WriteAtomic` ou para o NTFS. Não é caractere
reservado do Windows (`< > : " / \ | ? *`), e `validatePlatformPath` recusa ponto
e espaço no fim de componente, não travessão.

**O risco real é normalização Unicode, e ele existe.** As chaves do índice não
normalizam:

| ponto | derivação da chave |
|---|---|
| `index.publishNameLocked:163` | `strings.ToLower(path)` |
| `index.aliasKey` | `strings.ToLower(alias)` |
| `index.nomeChave` | `strings.ToLower(...)` |
| `index.ResolvePath:271` | `strings.ToLower(...)` |

Só caixa. Nenhuma delas aplica NFC/NFD, enquanto `text.Normalize` e
`parser.Slug` aplicam — as duas formas convivem no mesmo produto, para
propósitos diferentes, sem que nada diga onde uma acaba.

Consequência: `Capítulo` gravado em NFD (`i` + combining acute) e pedido em NFC
(`í` único) são **strings diferentes**, e `ResolvePath` devolve "not found" para
uma nota que existe. Num cofre só de Windows isso quase nunca aparece — o NTFS
devolve o que foi gravado e o cliente costuma mandar o mesmo. Aparece em cofre
sincronizado com macOS (que historicamente normaliza para NFD), que é
exatamente o cenário OneDrive que o projeto suporta. E este é um cofre em
português, onde acento é a regra e não a exceção.

O que precisa de teste, e hoje não tem: `note_create` seguido de `note_read` com
o mesmo caminho contendo (a) travessão, (b) acento em NFC, (c) o mesmo acento em
NFD, (d) emoji fora do BMP. É fixture barata e cobre uma classe inteira.

Lembrete que o item 1 torna urgente: a escrita **não passa** por
`vault.Resolve`, então `validatePlatformPath` — a única regra que hoje olha a
forma do componente — não roda em `note_create` nem em `note_move`.

## Alternativas de solução, por custo e retorno

Ordenadas. As três primeiras juntas resolvem o incidente sem tocar no parser.

**A — `offset` em `note_read`, e `match_offset` em `vault_search`.**
Custo: um campo em cada schema, três linhas de handler, um campo em `SearchHit`.
Retorno: fecha o caso por completo — busca localiza, leitura recorta, ambas com
código que já existe (`vault.ReadRange`, `Snippet.HighlightStart`). Devolver
<!-- check-doc-refs: ignore next_offset -- campo que a Task 106 vai criar; a ausencia dele E o achado -->
também `total_size`/`next_offset` para paginação honesta. **Fazer primeiro.**

**B — Ancorar o trecho no termo mais seletivo, e no casamento da frase quando
houver aspas.** Custo: médio; o IDF já é calculado em `CalculateBM25` e a posição
da frase já é calculada em `matchPhraseInNote` — os dois valores só precisam
sobreviver até `GenerateSnippet`. Retorno: o trecho passa a ser útil em nota
grande, que é onde ele mais importa. Sem isso, `vault_search` sobre documento
longo devolve sempre o começo do arquivo.

**C — Mensagem de erro que distingue "sem headings" de "não casou".**
Custo: trivial. Retorno: o modelo escolhe a próxima ferramenta em vez de gastar
uma rodada adivinhando. Vale acrescentar a saída sugerida na própria mensagem —
um erro que ensina o caminho alternativo vale mais que um erro correto.

**D — `note_outline`: uma tool nova que devolve o mapa da nota.**
Retorna a estrutura detectada com offsets: headings reais, e — separadamente e
rotulados como tais — candidatos sintéticos (parágrafo que é só negrito,
numeração hierárquica, setext). O modelo lê o mapa (barato, alguns KB) e recorta
com `offset`/`max_bytes` da alternativa A.

Prefiro isto a inventar headings no índice: não mente sobre o documento, não muda
o que `note_patch` aceita, não altera o peso de heading do BM25, e não exige bump
de `IndexCacheParserVersion`. É a resposta certa para "não sei onde está o que eu
quero neste arquivo de 255 KB", que é a pergunta real.

**E — Pseudo-heading no parser, como extensão goldmark.**
Reconhecer parágrafo cujo conteúdo inteiro é um único `Strong`, com nível derivado
da profundidade da numeração (`13` → 1, `13.1` → 2, `13.1.10` → 3), marcado
`Heading.Synthetic = true`. Também suportar setext, que é CommonMark legítimo e
não tem contra-argumento.

Retorno maior que D — conserta `note_read`, `note_patch`, âncora de wikilink e
peso de BM25 de uma vez. Custo maior também: mexe no corpus de 48 golden files,
exige `IndexCacheParserVersion++` (reconstrói o cache de todo cofre no boot
seguinte) e cria a pergunta de o que `replace_heading_and_section` deve fazer com
uma seção que não tem linha de heading. Decisão de produto, não de implementação.
`Synthetic` precisa aparecer em `note_metadata`, ou a tool passa a afirmar
estrutura que o arquivo não tem — que é a classe de defeito do item 7.

<!-- check-doc-refs: ignore from_text -- alternativa F, REJEITADA; o nome nunca deve existir no codigo -->
**F — `note_read` com `contains` / `from_text`.**
Recorta a partir da primeira ocorrência literal de um texto até a próxima
ocorrência de padrão semelhante. Resolve o caso sem parser e sem cache novo, mas é
uma segunda linguagem de endereçamento ao lado de heading e bloco — e as duas
divergem no dia em que uma ganhar tratamento de acento que a outra não tem. Só se
D e E forem recusadas.

**H — `paths` aceitando objeto por item.**
`["a.md", {"path":"b.md","heading":"X","max_bytes":4000}]`. Campos de topo
continuam sendo o padrão; o objeto sobrepõe. Uma forma de entrada em vez de
duas, e resolve o item 45 sem tornar ternária a exclusão mútua entre `path` e
`paths`. Baixo custo, alto uso — seis capítulos numa chamada em vez de seis.

**G — Limite de tamanho de resposta como contrato explícito.**
`note_read` sem `heading`/`block_id` numa nota de 255 KB devolve 255 KB e deixa o
host decidir o que fazer. O produto deveria ter opinião: teto padrão (o
`max_bytes` já existe, mas o padrão de 100.000 vem do handler e não é anunciado),
<!-- check-doc-refs: ignore next_offset -- campo que a Task 106 vai criar; a ausencia dele E o achado -->
`truncated: true` correto (hoje é o item 6) e `next_offset` para continuar. Sem
isso, toda nota grande é uma roleta contra o limite de tokens do cliente.

## O que este incidente diz sobre o processo

O modelo tinha as duas ferramentas carregadas e **escolheu a do concorrente para
ler**. Depois de falhar duas vezes com o gobsidian, recomendou ao usuário voltar
para o outro caminho. Nenhum gate do projeto mede isso: há gate de órfãos, de
lint, de rede, de formatação, de referência em documentação — e nenhum que
pergunte se uma tool resolve a tarefa que ela existe para resolver.

O que faltava era um teste ponta a ponta sobre uma fixture realista: nota grande,
convertida, com estrutura em negrito, CRLF e sem heading ATX. As fixtures atuais
são notas Obsidian idiomáticas, e nelas todo o produto funciona. **A premissa
"cofre Obsidian idiomático" nunca foi escrita como premissa** — e por isso nunca
foi questionada.

# ALTERNATIVAS DE ARQUITETURA

**`os.Root` no lugar do confinamento léxico** (item 4). Maior retorno isolado.
Elimina symlink, TOCTOU e a classe inteira do item 1.

**Ordinal de token no índice.** `TokenPosition{Start,End}` não sabe qual token é.
Guardar o ordinal (varint, delta-encoded, cabe no formato 6 sem inflar) habilita
de uma vez: frase exata correta, proximidade (`NEAR/3`), e ranking por
proximidade — três funcionalidades que hoje não têm como existir.

**Busca por prefixo e aproximada.** Só há casamento exato de termo (mais a
redução conservadora de 8 regras). O `baseSoA` guarda `termos` **ordenados**, o
que dá busca por prefixo em O(log n) de graça — `sort.SearchStrings` já está lá.
`[[art*]]`, autocomplete e tolerância a erro de digitação (Levenshtein sobre
candidatos por prefixo) são incrementais sobre a estrutura existente. É a lacuna
funcional mais visível para o usuário.

**Nomear SQLite/FTS5 como alternativa rejeitada.** O projeto reimplementou BM25,
índice invertido, codec binário próprio, arena mmap, cache de duas camadas e LRU
de trecho. É trabalho de alta qualidade, e o formato 6 provavelmente ganha do
FTS5 em memória compartilhada entre instâncias. Mas a decisão não está registrada
em lugar nenhum, e é a primeira pergunta de qualquer revisor externo. Registrar
com o argumento (CGO, um binário, controle do formato) — mesmo que a resposta
continue "não".

**Índice de metadados com granularidade de lock.** Um `sync.RWMutex` único
protege sete mapas; `Replace` segura o lock exclusivo durante `os.Stat` +
`ReadAll` + `parser.Parse` — I/O de disco **dentro** do lock de escrita. Toda
leitura concorrente para. Ler e parsear fora do lock e só publicar dentro dele é
uma mudança pequena com efeito direto na latência sob edição ativa.

**`Service.Index` não é abstração.** 12 métodos vazando `*index.Note`,
`index.Query`, `index.TagCount`, `index.Backlink`. `service` não pode ser testado
sem `index`, e a fronteira não protege nada. Ou estreitar para o que `service` de
fato usa, ou assumir o acoplamento e apagar a interface — a interface atual custa
indireção sem entregar substituição.

# GO 1.26 — O QUE O CÓDIGO PODE APROVEITAR

Fonte: <https://go.dev/doc/go1.26>, lida item a item e cruzada com o código.

## Ponto de partida: o porte já aconteceu sem ninguém decidir

```
go version go1.26.5 windows/amd64      GOTOOLCHAIN=auto
go.mod:  go 1.25.0
```

O `go` directive é **piso, não teto**. Com `GOTOOLCHAIN=auto` e o 1.26.5 instalado,
todo build e todo teste local já usam o compilador, o runtime e o GC de 1.26 —
inclusive a verificação que abre este relatório. O directive não é onde mora o
desempenho.

Medido, em cópia isolada do HEAD com `go 1.26.0` no directive:

| gate | resultado |
|---|---|
| `go build ./...` | 0 |
| `go vet ./...` | 0 |
| `GOOS=linux/darwin/windows go vet` | limpo nos três |
| `go test ./...` | 0 |
| `go test -race ./...` | **0** — 16 pacotes ok |
| `golangci-lint run ./...` (v2.12.2, built com go1.26.4) | **0 issues** |

Nenhuma dependência bloqueia: o `go` directive máximo entre elas é 1.25.0
(go-sdk, x/tools, x/sys, x/text).

## O que exige o bump do directive — sonda executada

```
go build ./internal/probe126/  → compila, silencioso
go vet   ./internal/probe126/  → errors.AsType requires go1.26 or later (file is go1.25)
```

`go build` passa e `go vet` reprova. O CI roda `go vet ./...` em três SOs: usar
API nova de 1.26 com `go 1.25.0` no go.mod **quebra o CI sem quebrar o build
local** — outra instância do "verde local não significa verde no CI".

Conclusão operacional: **ganho de runtime e de compilador vem do toolchain; API
nova exige o directive.**

Nota que corrobora manter o directive atrás: o `go mod init` do 1.26 passou a
gerar `go 1.25.0`. A recomendação de ficar uma versão atrás vem de quem escreve
o Go.

## 36. Pontuar o BM25 em espaço de IDs densos

*1.26 não habilita — torna muito mais lucrativa. A estrutura já existe e nunca
foi usada.*

`CalculateBM25` trabalha inteiramente em espaço de `string`:

```go
docTermFreqs := make(map[string]map[int]float64)
...
docTermFreqs[p.Path] = make(map[int]float64)   // UM MAPA POR DOCUMENTO
```

Numa consulta que casa 3.000 notas são **3.001 mapas**, mais `docsWithTerm` por
token e mais `docScores`. Cada um é um objeto com ponteiro que o coletor visita
em toda marcação.

A Task 88 já construiu o que falta: `baseSoA` atribui **IDs int32 densos**
(`idPorCaminho`, `caminhos[]`, `docLen[]`). O scorer nunca adotou.

| hoje | em espaço de ID |
|---|---|
| `map[string]map[int]float64` por documento | um `[]float32` achatado, ou acumulador esparso |
| `ix.DocLength(path)` — hash + `RLock` por chamada | `base.docLen[id]` — índice de array |
| hash de string no laço quente | comparação de int32 |
| milhares de objetos com ponteiro | **um bloco contíguo sem ponteiro nenhum** |

A última linha é o que muda com o Green Tea: um `[]float32` não tem ponteiro,
então sai do grafo de marcação inteiramente. Não são 3.000 alocações a menos —
são 3.000 objetos a menos para o GC **visitar em toda marcação**.

De brinde, resolve o **item 22** (`avgdl` O(N) por consulta): com `docLen` como
array, a soma vira varredura sequencial, ou um acumulador incremental.

Complicação honesta: a camada delta ainda é mapa de string. O desenho seria IDs
0..N−1 vindos do base e IDs ≥N atribuídos sob demanda ao delta. É trabalho real.

## 37. Estender o SoA ao índice de metadados

*1.26 torna mais lucrativa. É o grafo de ponteiros que sobrou.*

O índice invertido foi achatado; o de metadados não. `index.Index` são sete
mapas, e cada `*Note` carrega `Frontmatter`, `Tags`, `Aliases`, `Headings`,
`Blocks`, `Links` e `Inline`. Em 4.513 notas é a maior estrutura viva do
processo, feita exatamente do que o Green Tea varre pior: muitos objetos
pequenos alcançados por ponteiro.

(Verificado: `Inline` é alocado preguiçosamente em `parser/ast.go:71`, e
`Frontmatter` vem nil sem frontmatter. Não há desperdício de mapa vazio — o
custo é estrutural, não descuido.)

O caminho está pavimentado: `index_cache.gob` existe desde a Task 85 e
`persist.go` já carrega tudo por um ponto só. Carregar para arrays achatados com
arena de strings mais delta em mapa é o **mesmo** padrão de `soa.go`.

Adjacente e não explorado: `unique.Make` (Go 1.23) para internar
`CanonicalPath`. O mesmo caminho aparece hoje como chave em `notes`, valor em
`lowerPath`, item em `byName`, em `tags`, em `backlinks` e em `citantesPorNome`.

## 38. APIs com buffer do chamador, para o `variablemake` ter o que empilhar

*1.26 habilita o ganho; a mudança de assinatura é o que o destrava.*

O compilador aloca backing store de slice na pilha em mais casos — **só quando o
slice não escapa**. Hoje quase tudo escapa por retorno:

```go
func (ix *Inverted) Positions(term, path string) []TokenPosition {
    res := make([]TokenPosition, len(posList))   // escapa: é retornado
    copy(res, posList)
    return res
}
```

Os dois chamadores (`matchPhraseInNote`, `GenerateSnippet`) consomem e
descartam. Uma versão em estilo `append` —
`PositionsInto(dst []TokenPosition, term, path string) []TokenPosition` — deixa
o chamador reusar buffer, e um buffer pequeno passa a caber na pilha. Mesmo
raciocínio para `Postings`, que o comentário de `bm25.go:60` registra como
responsável por 371,40 MB num perfil.

Antes de mexer: rodar `-gcflags=-m` (o skill tem `escape_analysis.py`) e listar
o que **já** passou a ser empilhado sozinho. Otimizar o que o compilador
resolveu é dívida pura.

## 39. `context.WithCancelCause` no lifecycle

*Disponível desde 1.21. 1.26 padroniza o idioma ao fazer `NotifyContext`
cancelar com causa.*

Hoje o motivo vive em `l.reason` e quem está a jusante só vê `context.Canceled`.
É por isso que `shutdownExitCode` precisa **adivinhar** — e o CLAUDE.md registra
a sutileza: *"duas detecções de EOF independentes correm, e qual vence decide o
valor"*. Com `WithCancelCause`, `l.trigger(reason)` chama `cancel(...)` e
qualquer camada faz `context.Cause(ctx)` para saber por quê.

O texto de `reason=` é contrato do harness de órfãos: a causa acompanha, não
substitui.

Na mesma linha e independente de versão: `signals.go:29` faz `case <-ch:` e
**descarta o `os.Signal` recebido**. Qual sinal chegou é diagnóstico grátis,
hoje jogado fora. Vai num campo novo, nunca no `reason`.

## 40. Gate de goroutine vazada

*1.26 habilita, via `GOEXPERIMENT=goroutineleakprofile`.*

O gate de órfãos prova que **o processo** morre, nos quatro mecanismos. Não prova
nada sobre goroutine presa antes disso — e o desenho tem goroutines
deliberadamente fora do `WaitGroup`: `watchStdin`, as duas cópias de
`servePonteRemota`, e a etapa in-flight que pode ser "abandonada".

O perfil novo detecta goroutine bloqueada em primitiva inalcançável, que é
exatamente essa classe. Um cenário que roda o encerramento sob o experimento e
afirma que o perfil sai vazio converte "não vazou processo" em "não vazou nada".

## 41. `errors.AsType[T]` — 9 pontos, 8 concentrados

*1.26 habilita. Exige o directive.*

`service/write.go` repete quatro vezes:

```go
var hnf *writer.HeadingNotFoundError
var amb *writer.AmbiguousHeadingError
if errors.As(err, &amb) { ... }
if errors.As(err, &hnf) { ... }
```

`errors.AsType[*writer.AmbiguousHeadingError](err)` elimina a declaração
antecipada e o ponteiro-para-ponteiro — que é onde `errors.As` entra em pânico
se o tipo estiver errado. A checagem passa para o compilador. É integridade,
não estética. Também `service/errors.go:90`.

## 42. `netcheck` verificável por nome de método

*1.26 habilita, via `Dialer.DialUnix`/`ListenUnix`.*

A regra atual precisa provar que o **primeiro argumento** de `net.Dial` é a
constante `"unix"`, e por isso carrega `ehConstante`/`valorDe` — e ainda assim
deixa passar `net.Dialer` por método (item 19). Com `DialUnix`/`ListenUnix` a
rede está no **nome**: a regra vira "só estes dois métodos", impossível de furar
por variável, e cobre a forma com receptor.

Elimina também o workaround de `internal/ipc/dialUnix` — goroutine mais
goroutine de limpeza, ~22 linhas. Vale registrar que `Dialer.DialContext`
**sempre existiu**: o que prendeu o projeto a `net.Dial` foi a própria regra do
netcheck, não a biblioteca.

Ordem obrigatória: **corrigir o analisador antes de adotar**, senão a chamada
nova passa pelo guarda por acidente, não por permissão.

## 43. `os.OpenFile` com flags de Windows

*1.26 habilita. Exige o directive.*

Duas aplicações opostas, e a divisão importa:

- `FILE_FLAG_SEQUENTIAL_SCAN` no laço de boot (`buildInvertedIndex`, workers de
  `index.Build`) — leitura de milhares de arquivos em sequência.
- `FILE_FLAG_RANDOM_ACCESS` em `vault.ReadRange`, que faz `ReadAt` de faixas
  curtas — padrão oposto, hoje na heurística padrão.

Custo real: `os.ReadFile` não aceita flags, então são 14 chamadas trocadas por
`OpenFile` + leitura, atrás de build tag. É a única recomendação desta seção
cujo ganho não se justifica por mecanismo, só por hipótese — prototipar e medir
antes de assumir o custo.

Compõe com `os.Root`: `Root.OpenFile` aceita as mesmas flags, então adotar o
confinamento do item 4 não custa esta capacidade.

## 44. Itens menores

- **`testing.T.ArtifactDir()`** e a flag `-artifacts` — lugar padronizado para o
  teste depositar evidência, com o caminho impresso no log. Encaixa na cultura de
  "a saída real colada é o entregável" e em `scripts/audit_reports.ps1`.
- **`runtime/metrics`**: `/sched/goroutines` por estado, `/sched/threads:threads`
  e `/sched/goroutines-created`. `vault_stats` hoje expõe só `NumGoroutine`;
  contagem de criação revela churn e contagem por estado revela goroutine presa.
- **`go fix` revamped** mecaniza a higiene deste relatório: `interface{}` → `any`,
  `sort.Slice`/`sort.Strings` → `slices`, laços contados → `for range n`. Diff
  auditável. E `//go:fix inline` resolveria a consolidação das três normalizações

- **`fmt.Errorf("x")` aloca menos** — grátis, já ativo.

## O que parece aplicável e não é

Registrado para ninguém perseguir:

- **`io.ReadAll` ~2x mais rápido, −50% alocação.** Grep: **zero ocorrências** em
  `internal/` e `cmd/`. O projeto usa `os.ReadFile`, que tem caminho próprio
  (stat + buffer dimensionado) e não passa por `io.ReadAll`. **Ganho zero.** É o
  item que mais parece um presente e não é.
- **`os.Process.WithHandle()`** (pidfd/Handle). Parece a resposta para
  `lifecycle/parent_windows.go` e `daemon/pidvivo_windows.go`, que fazem
  `OpenProcess` + `GetProcessTimes` à mão. Não é: os dois consultam um PID que
  este processo **não criou** — o pai, e o dono do arquivo de lock. A leitura de
  `exitTime` continua sendo a resposta certa, e continua manual.
- **`os/signal.NotifyContext` com causa.** O `lifecycle` não usa `NotifyContext`
  e não deve passar a usar: ele é dono do próprio `cancel` e do `reason`.
- **Randomização do endereço-base do heap × arena mmap.** Verificado, não
  inferido: a suíte inteira, incluindo o pacote `search` com `mmap` e
  `unsafe.Slice`, passou `-race` sob 1.26. A randomização afeta o heap; a arena
  vem de mapeamento de arquivo, e o alinhamento de 8 bytes que `tentaAbrirArena`
  assume vem da página do SO. Sem impacto.
- `crypto/*`, `net/http`, `net/url`, `image/jpeg`, WebAssembly, riscv64, s390x,
  `cmd/doc` — fora do escopo do produto.
- **Segurança: 1.26 não traz nada para a lacuna real.** Travessia de caminho e
  symlink (itens 1 e 4) se resolvem com `os.Root`, que é **Go 1.24** — disponível
  há dois ciclos e não adotado.

### Correção de uma afirmação anterior deste relatório

Eu escrevi, na seção de desempenho e na análise de 1.26, que **"toda baseline
precisa ser regravada"** e que o inlining do `b.Loop()` invalidaria as medições
registradas. **A medição não sustenta isso**, e a afirmação era generalização do
release note sem olhar o formato dos benchmarks daqui: os corpos destes laços
chamam `svc.Search(...)` e `idx.Build(...)` — funções grandes, que nunca foram
candidatas a inlining em versão nenhuma. A correção do 1.26 vale para
micro-benchmark de corpo minúsculo, que este projeto não tem.

O que fica de pé, em forma mais estreita: `docs/bench-baseline.json` traz
`"runner": "... go 1.25 ..."`. **O arquivo é honesto e o campo é o contrato.** Se
o `bench.yml` subir para 1.26, a referência precisa ser regravada — não porque
os números mudaram de forma relevante, mas porque o campo passaria a descrever
uma coisa e o gate mediria outra.
